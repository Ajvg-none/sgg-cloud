1. LA EMPRESA Y SU ECOSISTEMA TECNOLÓGICO
================================================================================

La empresa es una óptica con tiendas distribuidas a nivel nacional. Para su 
operación diaria utiliza dos sistemas principales:

  1. GESVISION
     - Sistema de gestión de tiendas.
     - Maneja inventario, facturación, creación de órdenes de trabajo y 
       datos clínicos de los pacientes (fórmula, altura, DP, etc.).
     - Es el sistema "origen" donde las tiendas registran las órdenes de 
       los clientes.

  2. LENSWARE
     - Sistema de gestión de producción de laboratorio.
     - Se encarga de la fabricación física de los lentes.
     - Lee archivos en formato VCA (un formato específico que Lensware 
       interpreta para producir las órdenes).

PROBLEMA HISTÓRICO:
- No existía comunicación entre GesVision y Lensware.
- Las órdenes de trabajo no llegaban automáticamente al laboratorio para 
  su producción.
- Esto generaba retrasos, errores de transcripción y pérdida de trazabilidad.

SOLUCIÓN IMPLEMENTADA (MIDDLEWARE EN PRODUCCIÓN):
- Se desarrolló un middleware que:
  1. Extrae las órdenes de trabajo desde GesVision mediante su API.
  2. Transforma cada orden en un archivo VCA (formato que Lensware entiende).
  3. Genera un ticket ESC/POS para impresión en impresora Bixolon en el 
     laboratorio.
  4. Coloca el VCA en una carpeta de red que Lensware monitorea.
  5. Envía el ticket a un Agente de Impresión local (que corre en la PC del 
     laboratorio) para su impresión física.

- El middleware también cuenta con un módulo de "forzado" que permite 
  reintentar órdenes que fueron omitidas por errores de sincronización.

- Este middleware está en producción y ha demostrado ser estable y confiable.

================================================================================
2. PROBLEMÁTICA ACTUAL: GESTIÓN DE GARANTÍAS
================================================================================

A pesar de que el middleware resuelve la comunicación entre GesVision y 
Lensware para órdenes nuevas, existe un problema pendiente:

LAS GARANTÍAS SIGUEN SIENDO UN PROCESO MANUAL Y PAPELERO.

Cuando un cliente reclama una garantía por:
- Error de montura (la montura no calza, está dañada, etc.)
- Error de fórmula (la graduación no coincide con la receta)
- Defecto de fabricación (rayones, burbujas, etc.)

El proceso actual es:

  1. La tienda llena una nota de garantía a mano en papel.
  2. Adjunta esta nota a la montura física (o a los lentes).
  3. Envía ambos (papel + montura/lentes) al laboratorio por mensajería.
  4. El laboratorio recibe el paquete, revisa el papel, y procesa la garantía 
     manualmente.
  5. No hay registro digital del proceso, ni trazabilidad, ni seguimiento.

CONSECUENCIAS DE ESTE PROCESO:

  - Tardanza: El envío físico toma días.
  - Errores humanos: La información manuscrita es propensa a errores de 
    interpretación o transcripción.
  - Falta de trazabilidad: No se sabe en qué estado está cada garantía.
  - Pérdida de información: Los papeles se pueden extraviar.
  - Ineficiencia: El laboratorio debe reingresar datos manualmente en 
    Lensware, duplicando esfuerzo.

================================================================================
3. LA SOLUCIÓN PROPUESTA: SISTEMA DE GESTIÓN DE GARANTÍAS (SGG)
================================================================================

EL SGG ES UN NUEVO SISTEMA, INDEPENDIENTE DEL MIDDLEWARE, PERO QUE REUTILIZA 
SU LÓGICA. NO REEMPLAZA AL MIDDLEWARE, LO COMPLEMENTA.

OBJETIVOS PRINCIPALES:

  1. Digitalizar completamente el proceso de garantías.
  2. Eliminar el papeleo físico.
  3. Automatizar el flujo desde la tienda hasta el laboratorio.
  4. Proporcionar trazabilidad completa de cada garantía.
  5. Reutilizar la lógica del middleware existente para garantizar 
     compatibilidad con GesVision, Lensware y la impresora Bixolon.

VALOR AGREGADO:

  - Reducción del tiempo de procesamiento (de días a minutos).
  - Eliminación de errores de transcripción.
  - Trazabilidad digital completa.
  - Visibilidad para el administrador (todas las garantías en un solo lugar).
  - Integración con el ecosistema existente sin modificarlo.

================================================================================
4. ARQUITECTURA DEL SISTEMA
================================================================================

El SGG es un sistema de tres capas con un agente local para el laboratorio.

CAPA 1: FRONTEND (Web - React)
  - Accesible desde cualquier navegador.
  - Roles: Tienda (buscar, editar, guardar garantías), Administrador (gestión 
    de usuarios, configuración, dashboard).
  - Interfaz amigable y responsive.

CAPA 2: BACKEND (Nube - Node.js + Express)
  - API REST con autenticación JWT.
  - Persistencia en PostgreSQL (Prisma ORM).
  - Integración con GesVision (reutiliza lógica del middleware).
  - Lógica de colas y estados de garantías.
  - Comunicación con el Agente de Impresión (polling).

CAPA 3: AGENTE DE IMPRESIÓN (Local - Node.js)
  - Corre en la PC del laboratorio (Windows).
  - Hace polling al backend cada 5 segundos.
  - Cuando encuentra una garantía pendiente:
    1. Genera el archivo VCA en la carpeta de red (Lensware lo detecta).
    2. Genera e imprime el ticket ESC/POS en la impresora Bixolon.
    3. Notifica al backend que la garantía fue procesada.
  - Se instala como servicio de Windows (arranca automáticamente).

FLUJO COMPLETO DE UNA GARANTÍA:

  1. La tienda ingresa el número de orden en el SGG.
  2. El SGG consulta GesVision (usando lógica del middleware) y trae todos 
     los datos de la orden (fórmula, medidas, items, cliente).
  3. La tienda edita los datos si es necesario (corrige errores) y guarda 
     la garantía.
  4. El SGG asigna la garantía al laboratorio correspondiente y la pone en 
     estado PENDING.
  5. El Agente de Impresión (polling) detecta la nueva garantía.
  6. El Agente genera el VCA en la carpeta de red e imprime el ticket.
  7. El Agente notifica al SGG que la garantía fue procesada.
  8. El Admin puede ver todas las garantías en un dashboard centralizado.

5. REUTILIZACIÓN DE CÓDIGO DEL MIDDLEWARE (ESTRATEGIA CLAVE)
================================================================================

El SGG NO REESCRIBE la lógica de integración con GesVision ni la generación 
de VCA o tickets. En su lugar, COPIA Y ADAPTA las funciones ya probadas 
del middleware en producción.

MÓDULOS REUTILIZADOS (SIN MODIFICAR SU LÓGICA INTERNA):

  a) gesvisionApi.js
     - Autenticación con GesVision (obtención y refresco de token).
     - Manejo de reintentos con backoff exponencial.
     - Métodos: getGlassesOrder, getIssuedInvoice, getIssuedOrder, 
       getCustomer, getWarehouse, listGlassesOrdersPaginated.
     - Se copia íntegro; solo se ajustan las rutas de importación.

  b) fetchAndMapOrder() (extraída de orderSync.js)
     - Función pura que:
       1. Obtiene una orden de GesVision por su ID.
       2. Obtiene la factura emitida, el pedido emitido y los datos del 
          cliente.
       3. Mapea todos los datos (esferas, cilindros, ejes, adiciones, DP, 
          alturas, medidas de montura, items, etc.) a un objeto plano.
     - NO guarda en base de datos (solo devuelve el objeto mapeado).
     - Es la función "puente" entre GesVision y el nuevo sistema.

  c) generateVCAContent() (desde lensware.js)
     - Función pura que genera el contenido del archivo VCA a partir de 
       una orden y sus items.
     - Incluye la lógica de detección de montura (códigos que empiezan 
       con 'M') y cristales (códigos que empiezan con 'H', 'C', 'B', 'A').
     - Usa el código ACCN de la tienda para el campo correspondiente.
     - Se copia tal cual (sin dependencias de sistema de archivos).

  d) generateTicketText() y generateEscPosBuffer() (desde printer.js)
     - Funciones puras:
       1. generateTicketText: genera el ticket en texto plano formateado.
       2. generateEscPosBuffer: convierte el ticket a buffer ESC/POS 
          (formato que entiende la impresora Bixolon).
     - Se copian tal cual (sin dependencias de envío a agente o guardado 
       en disco).

RESTRICCIÓN:
- Queda terminantemente PROHIBIDO reimplementar estas funciones.
- Cualquier desviación de la lógica original DEBE justificarse y 
  someterse a revisión, ya que cambiar estos formatos rompería la 
  integración con Lensware y la impresora Bixolon.

7. CONSIDERACIONES TÉCNICAS IMPORTANTES
================================================================================

CONFIGURACIÓN SIN .env PARA RUTAS:
- Las rutas de red, IPs y puertos NO se manejan por variables de entorno 
  en el backend.
- Se almacenan en la base de datos (tabla laboratorios).
- Son editables desde el panel de administración.

SEGURIDAD:
- JWT para autenticación.
- Roles: Admin, Tienda, Laboratorio.
- Políticas de acceso: una tienda solo ve sus propias garantías (forzado 
  por backend).
- El Agente se autentica con API Key.

LOGS:
- Winston con rotación diaria.
- Logs accesibles desde el panel Admin.

CONCURRENCIA:
- Mecanismo de locks para el polling del agente.
- Cronjob que libera órdenes huérfanas (> 5 min en PROCESSING).

VALIDACIONES:
- En frontend (feedback inmediato) y backend (seguridad).
- Ejes: 0-180.
- Alturas: > 0.
- ACCN: 3 dígitos numéricos (obligatorio para cada tienda).
